## 3. Mechanism notes worth not rediscovering

- **n_layer 65, split units 66.** Blocks 0..64; blk.64 is the in-file MTP head (it is one of the 17
  KV-bearing blocks); unit 65 is the **output tensor**. `--tensor-split K,(66-K)` therefore lands
  exactly K units on CUDA0. Ties go to the later device by `upper_bound`, so integers are exact.
- CUDA0 = 5070 Ti, CUDA1 = 3080, **inverted vs nvidia-smi** (index 0 = 3080). serve.ps1 asserts the
  order before launch. Never derive split direction from `nvidia-smi -L`.
- Block bytes (Q3_K_XL, read from the GGUF by offset gaps, sum reconciles to the file exactly):
  GDN ≈ 170 MiB, full-attention ≈ 177 MiB, MTP blk.64 = 335 MiB, output.weight = 834 MiB,
  token_embd = 521 MiB (always CPU), mmproj 0.86 GiB (CPU by `--no-mmproj-offload`).
- KV: 4 KV heads × 256 head_dim × K+V. q8_0 = 2.125 KiB/token per attention layer; f16 = 4.0.
  Only 17 of 65 blocks have KV, so **the pin and the quantised draft KV are what make big context
  bootable** — pin alone left 251-321 MiB, q8_0 draft alone OOMed in `sched_reserve`.
- Per +4,096 tokens, measured slope: **3080 +84 MiB**, **5070 Ti +111 MiB**. KV alone predicts
  43.5 and 104. The 3080 extra is `n_embd × 2 B × tokens` (5,120 × 2 = 10 KiB/token → 40 MiB per
  4,096) — a cross-device activation buffer on the card that owns the tail layers and the output
  tensor. Calibrated, not explained. It is why the 3080 saturates about twice as fast as KV math
  suggests, and it is quant-independent.
- Boot is the peak, not the prefill: min-free-during-load equalled free-after-teardown in every
  run. KV is fully allocated at load with a fixed `-c`.
- The 4,096-token step is `4096`; `ladder-from-wsl.sh` passes `-Ceil` equal to `-Ctx` on every boot
  so a profile clamp can't quietly report a PASS for a size that never booted.

## 4. q4s / q4 — measured today, and where my prediction was wrong

**The falsification test failed to falsify, and taught more than a pass would have.** I predicted
q4s as-shipped would NOT boot (3080 short by ~710 MiB). It booted fine — at **33 MiB worst-case
free**. Direction right, magnitude wrong by ~750 MiB, and the cause was a bug in my own model: I had
attached the MTP draft KV to whichever device owns blk.64. It does not; the draft KV is allocated on
CUDA0 whether or not the block is pinned there. Reverted in `split-calc.py` with the measurement
as the comment. The same correction is why `config.ps1`'s note ("with the pin but f16 draft KV it
OOMed in sched_reserve") makes sense: that OOM was on CUDA0.

A/B on the same file and the same 155,648, one boot each (worst-case under a novel 23.8k-word cold
prefill; idle 9,379 / 15,272 read seconds before each boot):

| q4s config | 3080 worst | 5070 Ti worst | cold pp | decode |
|---|---|---|---|---|
| as-shipped: 17,8, no pin, f16 draft | **33 MiB** | 1,500 | 1,274.11 | 44.16 |
| 47,19 + `blk.64.*=CUDA0` + `-ctkd q8_0` | **879 MiB** | 1,005 | 1,138.96 | 46.88 |

So the pair is worth about **846 MiB on the 3080** — it is the difference between a config that sits
in the band where this box has reset the driver and one that clears the 400 line. It also costs
about 10.6% of prompt throughput and gains ~6% decode, but that is NOT a clean attribution: the
split, the pin and the draft-KV type all moved together. One-variable A/B is two boots if anyone
cares enough to separate them.

q4s ceiling ladder, with the pair, 47,19, 1024/256, post-boot free (5070 Ti / 3080):

    155,648  1,005 /   903   (worst under load 879)
    163,840    783 /   731
    172,032    559 /   555
    180,224    337 /   383   ← under the 400 line on the display card
    184,320    289 /   293
    188,416    289 /   207   ← under the 240 abort line on the 3080

Every size booted; decode 40.9-41.9 tok/s across the range. Read: **172,032 is defensible today,
180,224 is the aggressive choice, 188,416 is not certifiable.** Not yet written into config.ps1.

q4 (Q4_K_XL, 16.35 GiB) is still PREDICTED only — no boot yet, and the predictor now carries a
calibrated residual that varies by config (measured residuals today: 240 to 593 MiB per card, so
treat any prediction as ±300):

| q4 config | 5070 Ti margin | 3080 margin | read |
|---|---|---|---|
| 122,880 @ 17,8 as-shipped | +1,079 | **+221** | boots thin, same failure mode as q4s |
| 122,880 @ 47,19 + pair | +484 | +1,030 | fine |
| 131,072 @ 47,19 + pair | +263 | +865 | display card at the line |
| 135,168 @ **45,21** + pair | +596 | +339 | the balanced one — first target |
| 139,264 @ 47,19 + pair | +42 | +700 | won't be safe |
| 143,360 @ 45,21 + pair | +375 | +174 | marginal |

Why q4 wants **45,21** and q4s wants **47,19**: at 16.35 GiB the share that lands on CUDA0 is what
runs out first, so pulling one unit back to the 3080 buys the display card ~330 MiB. q4s (14.30
GiB) is the other way round. The split is per-file, not per-box — which is the mistake the old
17,8-on-every-row encoding invited.


### 4b. The ubatch A/B, run clean, and what it bought (q4s, 172,032, identical prompt)

Same profile, same ctx, same split, same pin, same draft-KV type, same 21,000-word prompt; only
`-Ubatch` differs. Each boot was cold because the cache directory is keyed on the batch, so neither
run could be a prefix hit. idle free was identical (9,379 / 15,291) for both.

| q4s @172,032 | post-boot 3080 / display | worst under load | cold pp | decode |
|---|---|---|---|---|
| 1024/**256** | 555 / 578 | 531 | 1,208.77 | 48.07 |
| 1024/**128** | 673 / 674 | **640** | 1,196.87 | 47.30 |
| delta | +118 / +96 | **+109 MiB** | **−1.0%** | −1.6% |

So halving ubatch is worth ~110-120 MiB per card for about **1% of prompt throughput** — an order of
magnitude cheaper than the 8% figure in serve.sh, which came from moving 2048/512 → 1024/256 → 512/128
(a 4× buffer reduction), not from one halving. Decode's 1.6% is inside the run-to-run spread.

Spending that margin on one more context step, both certified with the same cold 21,000-word prompt:

| row | config | worst under load | cold pp | decode | vs previous ceiling |
|---|---|---|---|---|---|
| q4s | **176,128** @ 47,19 + pair + 1024/128 | **525 SAFE** | 1,173.79 | 46.7 | +4,096 tokens, margin unchanged (525 vs 531) |
| q4 | **135,168** @ 45,21 + pair + 1024/128 | **429 SAFE** | 939.46 | 43.7 | +4,096 tokens, margin unchanged (429 vs 427) |

These two are NOT decomposed cleanly for q4 (the ctx step and the ubatch step moved together), so read
the q4 pp drop of −7.5% as the price of both, and the q4s −2.9% as the price of the ctx step. Neither
row is written yet: config still says `Ubatch = 256` with `Ceil = 172032 / 131072`. Writing 176,128 /
135,168 with `Ubatch = 128` needs one verification boot each, because both were certified through an
override rather than from the profile as written.

### 4c. Bumping the 4-bit rows by 4,096 / 8,192 on 1024/128 — done, and the model got exact

Calibrated the per-row residual from the two certified 1024/128 boots (display +287, 3080 +344 to
+367), then predicted forward on the measured slope (−111 display / −84 3080 per 4,096 — the slope is
quant-independent, so it transfers). Predicted vs measured post-boot:

| row | config | predicted display/3080 | measured display/3080 | worst under load | verdict |
|---|---|---|---|---|---|
| q4s | 180,224 @ 47,19 | 454 / 507 | 455 / 505 | **421** | SAFE |
| q4 | 139,264 @ 45,21 | 599 / 378 | 601 / 377 | **345** | MARGINAL — not written |
| q4 | 135,168 @ 45,21 | 709 / 461 | 713 / 461 | **429** | SAFE |

Within ~2 MiB on both. The predictor is now good enough to pick a ceiling in advance instead of
laddering blindly.

Written and verified from the profile with no overrides: **q4s Ceil 180,224, q4 Ceil 135,168, both
`Ubatch = 128`** — that is +8,192 tokens on q4s and +4,096 on q4 over the sizes written an hour
earlier, and +24,576 / +12,288 over their 09-19 rows. pi follows (176K / 132K labels, backups
`*.pre-q4-bump.bak`).

Two honest caveats on this step:

1. The verification boots reused the same 21,000-word prompt as the certification, so their prefill
   was a **disk-cache hit** (pp line empty — exactly the trap win/README.md documents). The margins
   they printed (447 both) are therefore *warm* readings; the cold numbers are the 421 and 429 above,
   which are what the ceilings rest on. Both still clear 400 cold.
2. The pp cost of the ubatch halving is **not** resolvable at n=1: four near-identical q4s readings
   spanned 1,173-1,208 tok/s (±3%) and q4's spanned 939-1,049 (±10%). So treat the earlier
   "−1.0% pp" and "−7.5% pp" as within noise. What IS solid is the margin gain, because it is a
   footprint difference measured against an identical idle baseline in the same run.

## 6. Harness inventory

- `split-test.sh` (new): stop → idle → boot → margin-check under a novel cold prefill → TSV with
  worst-free, pp, tg, verdict; falls back to a chosen split so a bad experiment never leaves the box
  unbooted. Knobs: `PROFILE CTX SPLITS KEEP DEFAULT_SPLIT EXTRA WORDS ROUNDS DRY=1`.
- `split-calc.py` (new): reads a GGUF's metadata and exact per-tensor bytes (offset gaps,
  self-checked against file size) and simulates llama.cpp's layer assignment, including the pin, and
  — after today's correction — the MTP draft KV landing on CUDA0 regardless of where blk.64 itself
  goes. Section 4's tables came from it. Residual (the part this model does not describe, mostly
  compute buffers) measured +240 to +593 MiB per card depending on config, so treat a prediction as
  +/-300 and confirm with a boot. Name is still `tmp-` — fold into `sizing.py` or rename it.
- Log rotation in win/config.ps1 + start.ps1 (new). Root cause it fixes: `Start-Process
  -RedirectStandard*` truncated `server.err.log` on every boot, so throughput evidence died with the
  boot it came from.
- Bugs found in WSL interop and my own scripts, all fixed: `powershell.exe -File start.ps1` never
  returns while the server grandchild lives (launch must be backgrounded, readiness polled via
  `/health`); `curl -w %{http_code} || echo 000` produced "000\n000" so a dead port looked alive;
  pp must be selected from big-prompt `prompt eval time` lines (a bare `tail -1` returns a 4-token
  warmup, ~31 tok/s); mawk silently never matches `[0-9]{4,}` interval regexes — filter with grep -E.
- Data rows produced today (untracked, ephemeral, mine): cert-229376.tsv, cert-233472.tsv,
  cert-q3-229376.tsv, ladder-q3-4719.tsv, ladder-q3l-4719.tsv, split-test-20260926-*.tsv. They are
  the raw evidence behind sections 2 and 4; the repo's own stability-*.tsv files were not touched.
- Known-remaining cosmetic bug, NOT fixed: `win/ladder-from-wsl.sh` builds its `CACHE` and `SPLIT`
  columns from a profile dry-run that does NOT receive `SPLIT=$SPLIT`, so the q4s ladder rows print
  `17,8` and `q4s-155648-…` for boots that were 47,19 at 163,840-188,416. `PIN`/`KVD` are right
  because `EXTRA` IS passed into that dry run — which is how I noticed the asymmetry. The directories
  on disk are correctly per-size and `-Ctx`/`-Ceil` are honoured; only the columns lie.
